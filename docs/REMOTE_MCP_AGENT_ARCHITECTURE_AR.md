# قرار هندسي: ربط AbanoubAI عبر MCP وتشغيل الوكيل المستمر

**الحالة:** مقترح هندسي — ليس تنفيذًا أو نشرًا  
**التاريخ:** 2026-11-16  
**النطاق:** تكامل خارجي آمن + أساس تشغيل مهام مستمرة

## القرار

نفصل بين وظيفتين:

1. **AbanoubAI Agent Runtime:** مسؤول عن المهام الدائمة، حفظ الحالة، الاستئناف بعد الانقطاع، الجدولة، التحقق، وسجل النشاط.
2. **Remote MCP Adapter:** واجهة معيارية تسمح لعميل متوافق (مثل ChatGPT عندما تدعم الخطة والسطح ذلك) بطلب معلومات أو تنفيذ أدوات محددة من AbanoubAI.

MCP وسيلة اتصال، وليس محرك تشغيل دائمًا. لا نعتمد على بقاء جلسة ChatGPT مفتوحة لتشغيل المهام.

## ما هو موجود بالفعل ويجب إعادة استخدامه

- مشروع TanStack Start وواجهات AbanoubAI.
- Supabase project: `wobfdslqlmvlatyrtgkd`.
- جداول ومكونات سابقة مرتبطة بـ `scheduled_jobs` وذاكرة الوكيل وسجل المحادثات.
- Cloudflare Worker الموجود في `cloudflare-worker/` كبوابة سحابية.
- GitHub Actions للاختبار والبناء.

قبل كتابة أي كود جديد، يجب تدقيق عقود الجداول الحالية، سياسات RLS، Edge Functions، ومصدر الـ Worker المنشور لتحديد ما يمكن إعادة استخدامه دون تكرار.

## المرحلة الأولى: MCP للقراءة فقط

أدوات أولية مقترحة، بعد المصادقة وربط المستخدم:

- `get_agent_status`: حالة الوكيل، آخر نشاط، وحالة kill switch دون كشف أسرار.
- `list_my_jobs`: قائمة مهام المستخدم نفسه مع ترقيم صفحات وحدود.
- `get_my_job`: حالة مهمة يملكها المستخدم، خطواتها العامة، وآخر نتيجة آمنة.
- `get_my_daily_report`: التقرير اليومي الخاص بالمستخدم.
- `search_my_project_docs`: بحث محدود في مستندات المشروع التي يملك المستخدم حق الوصول إليها.

لا تعرض الأدوات مفاتيح API أو رموز الجلسات أو بيانات مستخدم آخر أو أسرار الخادم أو سجلات حساسة كاملة. يجب أن تكون استجابات الأدوات محدودة الحجم، مع provenance ووقت التحديث.

## المصادقة والتفويض

- لا تقبل هوية من `user_id` يرسله العميل وحده؛ استخرج الهوية من جلسة موثقة.
- استخدم OAuth/Authorization وفق مواصفات MCP الحالية عند دعم العميل لذلك، مع نطاقات دقيقة ومدة صلاحية وتجديد آمن.
- تحقّق من issuer وaudience والتوقيع والانتهاء، ثم اربط كل استعلام بـ `auth.uid()` وسياسات RLS.
- لا تضع `service_role` أو مفاتيح المزودين في عميل MCP أو تعريفات الأدوات.
- لا تخزن bearer tokens في السجلات أو رسائل الخطأ.
- افصل بين read scopes وwrite scopes؛ الإصدار الأول read-only.

## المرحلة الثانية: مهام طويلة الأمد

إعادة استخدام نظام المهام الحالي بعد تدقيقه، مع التأكد من:

- حالات واضحة: queued, running, waiting_approval, succeeded, failed, cancelled.
- idempotency keys، checkpoints، bounded retries، lease/heartbeat، واستعادة المهام المتروكة.
- سجل أحداث قابل للتدقيق، وإظهار التقدم في الويب وAndroid.
- فصل planner عن executor وverifier؛ لا تعتبر المهمة ناجحة إلا بعد تحقق مستقل.
- إيقاف واستئناف وإلغاء واضح للمستخدم.

لا نضيف إطار تشغيل ثانٍ مثل eve أو Workflow SDK قبل إثبات أن البنية الحالية لا تحقق المتطلبات. تتم مقارنة الخيارات بناءً على تكاملها مع TanStack Start وSupabase وCloudflare، والتكلفة، والاستمرارية، وسهولة الاختبار.

## المرحلة الثالثة: الكتابة والموافقات — متوقفة

لا تُضاف أدوات لإنشاء/تعديل/حذف البيانات أو تنفيذ إجراءات خارجية قبل موافقة منفصلة على كل نطاق. لا يتم تفعيل AI routing أو external actions، ولا تغيير emergency kill switch. أي إجراءات حساسة تحتاج مراجعة صريحة، معاينة، idempotency، سجل تدقيق، وآلية تراجع مناسبة.

## قيود عميل ChatGPT

اتصال MCP المخصص يعتمد على دعم الحساب والمنتج وسطح الاستخدام. توثيق OpenAI الحالي يذكر أن اتصال MCP المخصص يتم عبر ChatGPT على الويب، وليس تطبيق الهاتف، وأن نطاقات الخطط والصلاحيات تختلف. لذلك:

- لا نعد المستخدم بأن التطبيق الحالي على Android سيستطيع الاتصال مباشرة بخادم MCP.
- نبني الواجهة المعيارية بصورة مستقلة، ثم نتحقق من أهلية الحساب والعميل قبل أي ربط.
- في الوقت الحالي، يظل تطبيق AbanoubAI نفسه هو واجهة الهاتف الأساسية، ويمكن استخدام تكامل GitHub المتصل ومهمة Automation الحالية في المتابعة.
- لا نطلب من المستخدم نسخ أسرار أو لصق access tokens يدويًا.

## اختبارات القبول

1. رفض الطلب غير المصادق عليه.
2. منع الوصول إلى مهام مستخدم آخر حتى عند تغيير المعرفات.
3. التحقق من issuer/audience/expiry.
4. منع تسريب الأسرار في النتائج والسجلات.
5. حدود حجم النتائج ومعدل الطلبات.
6. اختبارات prompt injection: محتوى المستندات لا يتحول إلى تعليمات تنفيذ.
7. إثبات أن MCP read-only لا يغير قاعدة البيانات.
8. استئناف مهمة بعد انقطاع العامل أو إعادة تشغيله.
9. تطابق حالة المهمة بين الويب وAndroid.
10. فشل مغلق عند تعطل المصادقة أو سياسة الصلاحيات.

## نتيجة تدقيق البنية واختيار محرك التشغيل — 2026-11-17

### ما ثبت من البنية الحالية

- \`cloudflare-worker/index.ts\` لا ينفذ مهامًا دائمة؛ هو بوابة محادثة \`/ai/chat\` ويعيد \`scheduled_jobs: false\`.
- جرد حساب Cloudflare المتصل أظهر Worker واحدًا باسم \`abanoupai-local-first-scheduler\`، دون أي Cloudflare Workflow أو Queue منشور وقت الفحص.
- جدول \`public.scheduled_jobs\` الموجود هو **تعريفات جدولة** (اسم، تعليمات، cron، المنطقة الزمنية، موعد التشغيل وآخر حالة)، وليس سجل تشغيل متينًا أو queue: لا توجد فيه lease أو heartbeat أو checkpoint أو idempotency key أو سجل أحداث مستقل.
- سياسة الجدول الحالية \`scheduled_jobs_owner\` تطبق \`auth.uid() = user_id\` على القراءة والكتابة للمستخدم المصادق.
- إضافة \`pgmq\` متاحة في كتالوج امتدادات Supabase، لكن \`installed_version\` غير مثبتة في المشروع عند الفحص؛ ولا توجد Queue منشأة يمكن إعادة استخدامها.
- مفاتيح الأمان الإنتاجية لم تتغير: \`emergency_kill_switch=true\`، و\`enable_ai_routing=false\`، و\`enable_external_actions=false\`.

### مقارنة الخيارات

| الخيار | ما يقدمه | ما لا يحله وحده | القرار |
|---|---|---|---|
| Cloudflare Workflows | تنفيذ متعدد الخطوات مع حفظ الحالة، إعادة المحاولة، الانتظار للأحداث، وإدارة الإيقاف والاستئناف والإنهاء | لا يغني عن قاعدة بيانات المنتج أو RLS أو سجل المستخدم طويل الأمد | **الاختيار المبدئي لمحرك التنفيذ** بعد إثبات المصادقة والتكلفة |
| Supabase Queues / pgmq | Queue داخل Postgres، رسائل durable، visibility timeout، أرشفة، وواجهة مراقبة | Queue تسليم رسائل وليست وحدها محرك orchestration متعدد الخطوات أو سجل UI كامل | **مؤجل** حتى يظهر احتياج فعلي لفصل ingress عن workers |
| \`scheduled_jobs\` الحالي + Worker | تعريف مواعيد المستخدم وبوابة Cloudflare الحالية | لا يوجد تنفيذ دائم، checkpoints، retries، leases أو resume مثبت | يُعاد استخدامه لتعريفات الجدولة فقط، ولا يوصف بأنه runtime |

**التصميم المبدئي:** Cloudflare Workflows ينفذ دورة المهمة، وSupabase يبقى مصدر الحقيقة لسجل المستخدم، الملكية، الأحداث والنتائج. لا ننشئ نظام Queue ثانيًا الآن. نضيف pgmq لاحقًا فقط إذا أثبتت القياسات الحاجة إلى buffering أو فصل producer/consumer.

**مقايضة التكلفة والحدود:** توثيق Cloudflare يذكر إتاحة Workflows على Free وPaid، لكن فوترة الخطوات والتخزين بدأت في 10 أغسطس 2026. في Free: 3,000 خطوة يوميًا، حتى 1,024 خطوة لكل Workflow و100 تنفيذ متزامن، واحتفاظ افتراضي بالحالة 3 أيام. في Paid: 500,000 خطوة شهريًا ضمن الحد المضمن ثم رسوم إضافية، مع حدود أعلى واحتفاظ قابل للضبط. يجب التحقق من خطة الحساب والاستخدام المتوقع قبل النشر؛ لا نفترض أن التشغيل مجاني بلا حدود.

### أول شريحة تنفيذية

PR #34 يضيف \`GET /agent/status\` للقراءة فقط. يتحقق من جلسة Supabase ثم يقرأ تعريفات الجدولة بنفس جلسة المستخدم ومفتاح النشر العام، ليبقى RLS هو حد الملكية. النتيجة محدودة بـ25 صفًا ومنقحة، ولا تتضمن التعليمات أو الأوامر أو النتائج التفصيلية. الاستجابة تصرح بوضوح أن \`durable_execution=false\` وأن runtime غير مهيأ. PR لم يُدمج أو يُنشر، ولا يمثل تشغيلًا مستمرًا.

### شروط الانتقال إلى التنفيذ الدائم

1. تثبيت مصدر Auth واحد والتحقق من جلسة المستخدم على الخادم، لا الاكتفاء بفحص \`iss\` محليًا.
2. تحديد خطة Cloudflare والحدود/التكلفة المتوقعة قبل إنشاء Workflow resource.
3. تصميم جدول run/event/checkpoint بعقود typed وقيود idempotency واحتفاظ محدود، مع RLS للقراءة الخاصة بالمستخدم.
4. تنفيذ harmless deterministic workflow أولًا، دون model calls أو external actions.
5. اختبار إعادة التشغيل، انتهاء lease، retry limits، الإلغاء، التكرار، وcross-user isolation.
6. عدم نشر endpoint عام أو تفعيل الكتابة/توجيه النماذج قبل اجتياز اختبارات الأمان والموافقة المنفصلة.

**الحالة:** اختيار معماري موثق ومبدئي؛ لا يوجد Workflow منشور أو عامل دائم أو مهمة اختبار تم تنفيذها على Cloudflare حتى الآن.
